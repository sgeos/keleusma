COMPLETION CONDITION — the operand-variant agreement sweep

Ordering is NOT a completion criterion. Any order of the work satisfies this, and
nothing here requires a particular branch, commit shape, or process step.

All of the following hold in the tree:

1. AGREEMENT IS DRIVEN, NOT INFERRED FROM SUPPORT.
   For each operation and operand type in the sweep, both the reference and the
   native code are EXECUTED and their results compared. A lowering that merely
   succeeds does not count as a pass.

2. EACH CASE HAS AN INPUT THAT LEAVES THE OPERAND'S NATURAL RANGE,
   so a case cannot agree by using values every wrong lowering would also get
   right.

3. A SHAPE THE REFERENCE REJECTS IS RECORDED AS REJECTED,
   not skipped silently, so absence from the matrix is visible.

4. THE POPULATION IS PINNED.
   A change in the number of cases fails, asking for the new variant to be placed
   in the matrix rather than for the number to be edited.

5. THE SWEEP STATES ITS LIMIT.
   It says that it covers the variants it was given rather than all that exist,
   and does not present a clean run as proof that no variant diverges.

6. NO NEW OPCODE, NO BYTECODE_VERSION CHANGE, AND NO EDIT TO src/ OR tests/ AT
   THE REPOSITORY ROOT.

7. THE BACKEND SUITE IS GREEN IN BOTH FLOAT CONFIGURATIONS, with counts
   re-derived rather than quoted.
