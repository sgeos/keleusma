COMPLETION CONDITION — checked arithmetic on Byte

Ordering is NOT a completion criterion. Any order of the work satisfies this, and
nothing here requires a particular branch, commit shape, or process step.

All of the following hold in the tree:

1. CHECKED BYTE ARITHMETIC AGREES WITH THE REFERENCE IN VALUE AND IN ARM.
   For each checked operation that admits an overflow arm on Byte operands, a
   program is driven at values inside the byte range and outside it, and the
   native result matches the reference both in the value produced and in which
   arm ran.

2. THE OVERFLOW ARM IS SHOWN TO BE SELECTED.
   A subject distinguishes the arms, so agreement cannot hold while the flag is
   always zero.

3. THE SCOPE IS ESTABLISHED BY PROBING, NOT ASSUMED.
   The tree records which checked operations admit a Byte overflow arm and which
   do not, measured rather than inferred from the two that were found.

4. AN OPERAND OF UNKNOWN WIDTH DOES NOT SILENTLY TAKE THE INTEGER PATH.
   Where the backend cannot establish that the operands are bytes, it refuses or
   is shown to be unable to reach the case.

5. THE SUPPORT CENSUS DISTINGUISHES OPERAND VARIANTS.
   It no longer reports support for an opcode on the strength of one operand
   type, and it fails when a new variant appears unprobed. It is non-vacuous: it
   still finds the cases it already covered.

6. NO NEW OPCODE, NO BYTECODE_VERSION CHANGE, AND NO EDIT TO src/ OR tests/ AT
   THE REPOSITORY ROOT.

7. THE BACKEND SUITE IS GREEN IN BOTH FLOAT CONFIGURATIONS, with counts
   re-derived rather than quoted.
