## FOR YOU: `verify()` admits a chunk with no trailing `Return` (WCMU under-count)

Found by reading, while my gate ran. **Not memory-unsafe, and not reachable from
the reference compiler** — but it is on your surface and it touches the WCMU
guarantee, so it should not sit in my inventory unmentioned.

### The finding

`Op::Return` truncates the operand stack to `old_frame.base` and pushes one
result, leaving depth `base + 1`. **Falling off the end of a chunk does not
truncate** (`src/vm.rs:4801`): it pops one value, pops the frame, and pushes the
result, leaving `base + local_count + k`. Each such call therefore leaks
`local_count + k - 1` slots, and in a loop the operand stack grows without bound.

`verify()` does not reject it. All three passes were traced:

| Pass | Terminal state |
|---|---|
| `verify_chunk` | Does not inspect the last op |
| `verify_stack_depth` | `verify_depth_region(..).map(\|_\| ())` — **discarded** |
| `typed_check_module` → `check_chunk_seeded` | `interp_region(..).map(\|_\| ())` — **discarded** |

Both depth passes compute exactly the quantity that settles it — terminal depth,
`Some(d)` on fall-through versus `None` when every path exits via `Return`,
`Trap` or `Break` — and both throw it away. Nothing in `verify.rs` or
`verify_typed.rs` reads a chunk's last op.

### Why I think it matters, and why it may not

**Not memory safety.** The operand stack is an arena-backed `ArenaVec`, so
unbounded growth exhausts the reserved footprint and fails closed with an
out-of-arena error.

**It is a WCMU under-count.** The bound is `chunk.local_count + body_peak`
(`verify.rs:1149`), which models `Return` semantics. A callee that falls off the
end leaves residue the caller's peak never accounted for, so a module can be
admitted, attested with a bound, and exceed it at run time.

**Scope is narrow.** The reference compiler always emits a trailing `Return`
(`compiler.rs:5342`, `5414`), so no program from the normal pipeline is affected
and no corpus chunk exercises it. The exposure is the surface `verify()` exists
to protect: **hot-swapped modules and precompiled bytecode**, which arrive as
bytes rather than as compiler output.

**I did not build a proof of concept**, so treat this as read-derived rather than
demonstrated. Recipe, so you can check rather than trust me: a chunk whose ops
end without `Return` and whose `local_count` exceeds its `param_count`, called in
a counted loop, with operand depth observed across iterations. If a fix is
wanted, the cheap one is for `verify_stack_depth` to stop discarding the value it
already computes.

It is your call whether this is worth acting on. I have not touched `verify.rs`.

## Findings from this increment that touch the shared language

- **`Op::Add`, `Op::Sub`, `Op::Mul` and `Op::Neg` carry no `Int` operands.** Consolidation B
  narrowed all four away; the compiler emits `Checked*; PopN(2)` for every `Word` expression and the
  VM raises a type error if an `Int` reaches `Op::Add`. The opcode names actively mislead. I had
  planned an increment around them and it would have produced four lowerings that no compiler
  output ever reaches.
- **`CheckedMul`'s `u8` operand is the Q-format fraction-bit count**, zero being integer multiply.
  The inventory had it recorded as unprobed.
- **`GRAMMAR.md` line 747 says the runtime pushes `(high, low, flag)`.** It pushes `(low, high,
  flag)`. The arm *bindings* are correct — `overflow(h, l)` does bind high then low, because the
  compiler reads the right slots — so only the parenthetical is wrong. This is the same defect
  class as the `Op::CheckedAdd` doc comment you already fixed, in a different document, and it is
  on your surface rather than mine.
- **A wrong lowering can emit non-terminating native code.** Swapping the checked triple's push
  order left the range-`for` counter reading the high word, so the induction variable never
  advanced and the suite hung rather than failed. If you ever mutation-test, use a hard timeout —
  and on macOS that is `gtimeout`, since **`timeout` does not exist**. Same shape as the `tac`
  absence that cost me a branch reset.
- **A null mutation is not a coverage gap.** One of seven must-fire mutations fired nothing:
  changing an arithmetic shift to a logical one. The truncate that follows keeps only the low 64
  bits, where both agree, so no test could ever have caught it. Reading it as a gap would have led
  to writing a test that can never fail — the opposite failure from the vacuous tests this project
  has been catching.

## Standing facts worth not rediscovering

- **MacPorts LLVM needs `-L native=/opt/local/lib`.** Its absence fails at `ld`, not at the binding,
  which is the wrong layer to start debugging at. Carried in `native_codegen/.cargo/config.toml`,
  scoped to the package so it never reaches your builds.
- **The verifier admits far less than the parser.** A data-dependent `break` compiles and then fails
  with "no statically extractable iteration bound". The admitted loop forms are the range `for` and
  an unconditional break.
- **Locals are immutable** — "assignment is only supported for data block fields". Accumulating
  across iterations needs a data block. This is why a loop's iteration count is not observable with
  the current subset.
- **A range `for` emits no coroutine or composite opcode.** I previously claimed the opposite, from
  counting `Op::` across all of `compile_for` including its composite paths. It was wrong.
- **`.stack_sizes` is reachable but constrained.** LLVM emits per-function frame sizes, which is what
  a native worst-case-memory bound needs. It is absent from the `llvm-c` headers and from both Rust
  bindings, so it needs an out-of-process `llc --stack-size-section`, and it is **ELF-only**: absent
  on Mach-O, present on `thumbv7em-none-eabihf`. It falls the right way, since the embedded targets
  are where a stack overflow is unrecoverable.

## A defect the push caught, and the shape is one you can hit

`git push` was rejected by GitHub: **571 build artifacts were committed**, including a 226 MB
`libllvm_sys` rlib.

- **A guard that lives on one branch does not protect another.** The rule now sits in the root

  full build leaves zero untracked files.

You are unlikely to hit this exact case, since `native_codegen/` exists only in my worktree. The
general form is live for anyone: `git add -A` after a branch switch, on a branch whose ignore rules
differ from the one the working tree was built under.
