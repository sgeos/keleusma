## **WORKSTREAM E HAS REAL WORK IN IT: NO VERIFIED FIGURE BOUNDS THE BACKEND'S REGION**

**This is the Order-4 gate and the project's whole value proposition.** The bytecode is the
verification artefact; native compilation must not invalidate the bounds proven on it. `region.rs`
claims exactly that, in a comment: a region of unspecified origin *"would put the backend's memory
outside the arena's accounting, and transferring that bound is the whole property this lowering
exists to preserve."*

**Naming the provenance is not the same as a verified figure covering it, and measurement separates
the two.** Eleven corpus modules demand MORE arena than the verifier's heap figure:

```
rogue_ai_hunter.kel  backend 120 bytes vs verified heap 48
rogue_player_ai.kel  backend 120 bytes vs verified heap 24
rogue_combat.kel     backend  64 bytes vs verified heap 16   (4x)
```

**THE CONCLUSION IS NEGATIVE AND NEEDS NO SEMANTICS TO BE SETTLED.** If `max_heap_bytes` bounded the
backend's demand, no module could exceed it. Modules do. **Therefore it does not bound it.**

The mechanism explains the direction: the verifier's heap counts `Op::NewComposite`'s allocation in
the arena's **TOP** region, where the virtual machine puts composite bodies. The backend takes its
region from the arena's **BOTTOM** section and gives every call site a **disjoint** block, so two
calls to one callee cannot overwrite each other. Different pool, different reuse discipline, larger
total.

**NOT A SAFETY DEFECT, and it must not be reported as one.** The host is told explicitly to supply
the region and how large it must be; nothing reads memory it was not given. What is missing is the
**guarantee**, not a check: a host provisioning from the verified worst-case-memory figure alone
would size the top region correctly and the bottom region **not at all**. That is the first
concrete, demonstrated item of Workstream E scope this line has had.

**WHERE THE GAP IS, WHICH IS THE ACTIONABLE PART.** `auto_arena_capacity_for` is the documented way
for a host to size an arena, and it returns the sum of exactly four terms: operand-stack bytes,
call-frame bytes, the module's auxiliary arena bytes, and `max_heap_bytes`. **None of them is the
backend's region**, and `max_heap_bytes` — the only term that could plausibly cover composite bodies
— is the one measured to be exceeded. So the gap is not a figure being slightly low: **the sizing
API has no term for that pool.**

**AND HALF OF CLOSING IT WAS THIS LINE'S ALL ALONG — I FRAMED IT TOO NARROWLY.** I recorded this as
needing an operator ruling because closing it "means adding a term to `auto_arena_capacity_for`",
which lives in read-only `src/vm.rs`. **That is one way to close it, not the only one.** The backend
knows its own demand, and a host can add that figure to whatever the runtime returned. That half
needed nobody, and I referred it upward anyway.

**`region::host_arena_supplement_bytes(module)` now publishes the missing figure**, rooted at the
entry and folded through calls, taken from the same planner the lowering uses. A host can close the
gap today with no runtime change.

**IT IS A WEAKER GUARANTEE AND THE DOCUMENTATION SAYS SO.** A figure the host must remember to ADD
is not one the sizing function includes; **a host calling only `auto_arena_capacity_for` is still
under-provisioned for native execution.** Publishing the term does not change that.

**THE SOUNDNESS PROPERTY IS THE CONTENT, NOT THE WRAPPER.** A function that only changes an argument
list is decoration. The check nobody had made is that **the entry-rooted total DOMINATES every
reachable chunk's own plan** — if the recursion under-counted anywhere, a host sizing from it would
under-provision and the backend writes at compile-time offsets into that memory. Measured: **1025
chunk comparisons across 30 modules with non-zero demand, zero shortfalls.** Mutation-verified —
dropping the call folding makes it fail.

**WHAT REMAINS THE OPERATOR'S IS NOW BETTER POSED**: not *is there an unaccounted pool* but *should
the runtime absorb a term the backend already publishes*. That is an arena-accounting decision and
it changes what every host is told to provision.

## DO NOT LOWER THE GENERIC ARITHMETIC CLUSTER YET. A FLOAT VALUE ALREADY REACHES THE LOWERING

**The backend has NO float support**: zero `f64_type`, `float_type` or `FloatValue`, and no float

**AND A FLOAT VALUE ALREADY REACHES THE OPERAND STACK.** `fn p(a: Float) -> Float { a }` lowers

`Op::Add` is emitted for `Byte` **or** `Float` operands (`Word` takes the `Checked` forms). Lowering

## I MANUFACTURED A DIVERGENCE WITH AN ASYMMETRIC PROBE, 2026-08-20

**Read this before trusting any probe result in this file, mine included.**

I reported a "candidate divergence": under a probe resume convention, `wire.kel` passed the
virtual-machine side and then trapped natively, so the native side appeared to fault where the
virtual machine completed. **It was an artefact of my own instrument.**

**The probe changed ONE side.** It replaced the virtual machine's resume value with the entry's
initial argument. The native stream driver does not use the argument vector at all: the arm is
`for t in 0..ticks { f.call(t, sp, pp, rp) }`, and it passes the TICK, always. So the two sides
received different inputs, and a divergence under different inputs is not a divergence at all --
it is two different programs.

**The symmetric measurement says the opposite.** Driven with the SHIPPED convention and no source
change, both sides fault at **tick 19**: `IndexOutOfBounds(1570808, 65536)` on the virtual machine,
`SIGTRAP` natively. That is agreement in the fact and the position of the fault. It is NOT agreement
in its identity -- **SIGTRAP proves a fault, not which** -- and this file already says so.

**What caught it was asking a cheaper question of the SAME instrument.** The child harness
`trap_child_runs_one_module_natively` already ran one module natively with no modification, so the
question "does it trap under the CURRENT convention too?" cost nothing to ask. It did. Once the
trap was there without my probe, the probe could not be what caused it.

**The rule, in the form that would have prevented it:** before reporting a difference between two
sides, verify that both sides were given THE SAME INPUT. An instrument that feeds them differently
will produce a difference every time, and it will look exactly like a finding.

### The two ABI decisions this arc made, both host-visible

- **`kel_native_<mangled>`, called directly.** Name-derived rather than index-derived because
  `Vm::run` binds natives BY NAME through `native_name(idx)`; an index would tie the object
  file to declaration order. Each separator character becomes one underscore, so `host::two`
  and `host_two` stay distinct — collapsing `::` reads better and collides the likelier pair.
  Not injective even so, so a **module-level** precondition refuses a collision, because no
  call site can see a hazard that is a property of a pair.
- **`{ i64 len, [n+1 x i8] bytes }` for a static string, address in the slot.** The length is
  explicit because a Keleusma string is a byte string: a raw NUL inside a source literal is
  accepted by the lexer, VERIFIED not assumed, so a bare `char*` would truncate one. The
  trailing NUL is added anyway for an ordinary C host.

  **OPERATOR DECISION OWED.** On the virtual machine a string-taking native receives a
  marshalled `String`; natively it receives this pointer. The two embeddings are therefore
  **not source-compatible** for a string-taking native. Inherent to ahead-of-time lowering
  rather than a defect, but it is new host surface and the operator may want a different
  shape.

### THE MEMORY MODEL, per operator correction 2026-08-12

The bound has **three parts**, not two, and conflating them is what produced the retraction above.

- **`heap_bytes` transfers EXACTLY.** It counts arena allocations, and `NewComposite`'s `byte_size` is
  already summed by the worst-case-memory pass. Native code allocating from the same fixed-size arena
  inherits the bound.
- **`stack_bytes` has no native counterpart.** It counts virtual-machine operand slots, which live in a
  growable vector in the interpreter and in registers natively.
- **The native machine frame is a third quantity** the bytecode never described.

**Composite bodies go in the ARENA, not on the machine stack.** A backend reaching for the stack because it
is nearer would convert a bounded quantity into an unbounded one for no benefit. That was an actual error in
an article draft, caught by the operator.

## Standing facts worth not rediscovering

- **MacPorts LLVM needs `-L native=/opt/local/lib`.** Its absence fails at `ld`, not at the binding,
  which is the wrong layer to start debugging at. Carried in `native_codegen/.cargo/config.toml`,
  scoped to the package so it never reaches your builds.
- **The verifier admits far less than the parser.** A data-dependent `break` compiles and then fails
  with "no statically extractable iteration bound". The admitted loop forms are the range `for` and
  an unconditional break.
- **Locals are immutable** — "assignment is only supported for data block fields". Accumulating
  across iterations needs a data block. This is why a loop's iteration count is not observable with
  the current subset.
- **A range `for` emits no coroutine or composite opcode.** I previously claimed the opposite, from
  counting `Op::` across all of `compile_for` including its composite paths. It was wrong.
- **`.stack_sizes` is reachable but constrained.** LLVM emits per-function frame sizes, which is what
  a native worst-case-memory bound needs. It is absent from the `llvm-c` headers and from both Rust
  bindings, so it needs an out-of-process `llc --stack-size-section`, and it is **ELF-only**: absent
  on Mach-O, present on `thumbv7em-none-eabihf`. It falls the right way, since the embedded targets
  are where a stack overflow is unrecoverable.
