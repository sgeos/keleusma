### The next increment

**Group 2's division family**: `Div`, `Mod`, `CheckedDiv`, `CheckedMod`. **A guard is mandatory,
not optional**: division by zero is undefined behaviour in LLVM, and so is `i64::MIN / -1`. But do
not assume both forms trap. The VM's `Op::CheckedDiv` **reifies a zero divisor as flag `3`** with
the numerator in the low slot, so the handled `zero_divisor(n)` arm can bind it; only the unhandled
case traps. Read the VM arm before lowering — the checked and unchecked forms differ, and the
opcode names do not say so.

The previous entry here said the next increment was `Add`, `Sub`, `Mul` and `Neg`. **That was
wrong and the work is done differently**; see the correction at the top of the inventory. Those
four carry no `Int` operands.

Rules that bind the work: **no new opcode and no `BYTECODE_VERSION` bump without operator
authorisation**; the differential oracle against the VM is the correctness signal; every structural
check needs a **must-fire and a must-not-fire case**; anything irreversible or outward-facing needs

## Findings from this increment that touch the shared language

- **`Op::Add`, `Op::Sub`, `Op::Mul` and `Op::Neg` carry no `Int` operands.** Consolidation B
  narrowed all four away; the compiler emits `Checked*; PopN(2)` for every `Word` expression and the
  VM raises a type error if an `Int` reaches `Op::Add`. The opcode names actively mislead. I had
  planned an increment around them and it would have produced four lowerings that no compiler
  output ever reaches.
- **`CheckedMul`'s `u8` operand is the Q-format fraction-bit count**, zero being integer multiply.
  The inventory had it recorded as unprobed.
- **`GRAMMAR.md` line 747 says the runtime pushes `(high, low, flag)`.** It pushes `(low, high,
  flag)`. The arm *bindings* are correct — `overflow(h, l)` does bind high then low, because the
  compiler reads the right slots — so only the parenthetical is wrong. This is the same defect
  class as the `Op::CheckedAdd` doc comment you already fixed, in a different document, and it is
  on your surface rather than mine.
- **A wrong lowering can emit non-terminating native code.** Swapping the checked triple's push
  order left the range-`for` counter reading the high word, so the induction variable never
  advanced and the suite hung rather than failed. If you ever mutation-test, use a hard timeout —
  and on macOS that is `gtimeout`, since **`timeout` does not exist**. Same shape as the `tac`
  absence that cost me a branch reset.
- **A null mutation is not a coverage gap.** One of seven must-fire mutations fired nothing:
  changing an arithmetic shift to a logical one. The truncate that follows keeps only the low 64
  bits, where both agree, so no test could ever have caught it. Reading it as a gap would have led
  to writing a test that can never fail — the opposite failure from the vacuous tests this project
  has been catching.

## Standing facts worth not rediscovering

- **MacPorts LLVM needs `-L native=/opt/local/lib`.** Its absence fails at `ld`, not at the binding,
  which is the wrong layer to start debugging at. Carried in `native_codegen/.cargo/config.toml`,
  scoped to the package so it never reaches your builds.
- **The verifier admits far less than the parser.** A data-dependent `break` compiles and then fails
  with "no statically extractable iteration bound". The admitted loop forms are the range `for` and
  an unconditional break.
- **Locals are immutable** — "assignment is only supported for data block fields". Accumulating
  across iterations needs a data block. This is why a loop's iteration count is not observable with
  the current subset.
- **A range `for` emits no coroutine or composite opcode.** I previously claimed the opposite, from
  counting `Op::` across all of `compile_for` including its composite paths. It was wrong.
- **`.stack_sizes` is reachable but constrained.** LLVM emits per-function frame sizes, which is what
  a native worst-case-memory bound needs. It is absent from the `llvm-c` headers and from both Rust
  bindings, so it needs an out-of-process `llc --stack-size-section`, and it is **ELF-only**: absent
  on Mach-O, present on `thumbv7em-none-eabihf`. It falls the right way, since the embedded targets
  are where a stack overflow is unrecoverable.
